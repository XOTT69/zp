# Корпоративний вхід

Робочий логін → активний обліковий запис LDAP/AD → корпоративна email-адреса → користувач Slack → особисте повідомлення з одноразовим кодом → сесія калькулятора.

Це вхід через код у Slack із перевіркою членства в каталозі. Калькулятор не просить LDAP-пароль і не надсилає його в месенджер. Працівники отримують доступ до всіх 13 калькуляторів; редагування ставок залишається лише адміністратору.

## Що підготувати адміністратору

1. Створити Slack App із `docs/slack-app-manifest.json`, встановити у робочий workspace. Записати Bot User OAuth Token у серверну змінну `SLACK_BOT_TOKEN` у Vercel. Дозволи: `users:read.email` і `chat:write`; читання повідомлень не потрібне.
2. Підключити Upstash Redis, записати REST URL і токен у змінні з `.env.example`.
3. Надати сервісний LDAP-акаунт лише для читання: URL `ldaps://…`, bind DN, пароль і base DN. LDAP `mail` має збігатися з email у Slack. `LDAP_EMAIL_DOMAINS` обмежує дозволені корпоративні домени. Типовий фільтр налаштовано на Microsoft AD й активні акаунти. Для іншого каталогу IT має задати відповідний фільтр активності з обов’язковим `{{login}}`.
4. Перевірити доступність LDAP із середовища хостингу. Якщо він доступний лише через VPN, потрібен HTTPS-міст у корпоративній мережі або розміщення Node-сервера всередині неї. Доступ локального ноутбука через VPN не означає, що Vercel може підключитися.
5. Встановити `LDAP_SLACK_ENABLED=true` та redeploy. Спочатку перевірити тестового працівника в preview. Лише після успішної перевірки можна вимкнути коди ролей: `ROLE_CODE_LOGIN_ENABLED=false`. Це вимикає також адміністративний код; для адмін-панелі залишайте коди ввімкненими до окремого погодженого способу призначення адміністратора.

Секрети вводяться в Environment Variables, а не в репозиторій чи публічний чат. Шаблон не містить робочих доступів.

## Контракт HTTPS-моста

За наявності `LDAP_BRIDGE_URL` та `LDAP_BRIDGE_TOKEN` замість прямого LDAP виконується:

```http
POST /directory/lookup
Authorization: Bearer <server-only bridge token>
Content-Type: application/json

{"login":"employee.login"}
```

Активний працівник: HTTP 200, `{"active":true,"email":"employee@example.invalid","displayName":"Ім’я"}`. Невідомий або заблокований: HTTP 200, `{"active":false}`. Помилка каталогу: HTTP 503. Міст має перевіряти токен, екранувати LDAP-фільтр, перевіряти активність, обмежувати частоту запитів і не логувати секрети. Міст розгортає IT у мережі з доступом до каталогу; готового корпоративного endpoint у цьому репозиторії немає.

## Обмеження й перевірки

- Код: 6 цифр, 5 хвилин, одна успішна спроба, максимум 5 неправильних спроб. Повторна видача не частіше 60 секунд; 10 запитів із IP за 15 хвилин. Redis зберігає HMAC коду, а не сам код. Порівняння, лічильник спроб та споживання — атомарний Lua-скрипт.
- Перевіряється також останній виданий код для логіна й активність LDAP при завершенні входу. Під час уже відкритої сесії LDAP не опитується; корпоративна сесія має абсолютний термін 8 годин.
- Cookie: HttpOnly, Secure на хостингу, SameSite=Lax. Зміна `AUTH_SESSION_VERSION` відкликає всі сесії; зміна коду ролі відкликає сесії цієї ролі. Вимкнення корпоративного входу відкликає корпоративні сесії.
- Автотести ізольовано перевіряють логіку й транспортні контракти. Вони не замінюють інтеграційну перевірку справжнього LDAP, Slack і виконання Lua в Redis.
- Перед production перевірити: активний/неактивний працівник; правильний/неправильний/прострочений/повторний код; п’ять помилок; перевидача; паралельне використання одного коду; недоступність Redis та Slack. Для реальних повідомлень використати погоджений тестовий акаунт.

Офіційна документація: [users.lookupByEmail](https://docs.slack.dev/reference/methods/users.lookupByEmail/) і [chat.postMessage](https://docs.slack.dev/reference/methods/chat.postMessage/).
