# Корпоративний вхід

LDAP-логін → активний Slack-профіль із відповідним полем **About me → LDAP** → одноразовий код у Slack → калькулятор. Email та пароль LDAP не потрібні. Основний режим `CORPORATE_AUTH_SOURCE=slack-profile` не підключається до LDAP/AD-сервера. LDAP тут — назва робочого логіна у профілі.

## Автоматичний пошук LDAP

Власник дозволив перегляд Slack-профілів для автоматичного пошуку LDAP. При `SLACK_DIRECTORY_ENABLED=true` працівник одразу вводить LDAP на сайті й отримує код у Slack, без попередньої команди `/zp`.

Оновлення читає сторінки `users.list` та поле LDAP через `users.profile.get` активних звичайних працівників потрібного workspace. Redis зберігає HMAC логіна та Slack ID, без email і копій профілів. Дубльовані LDAP блокуються. Знайдений кандидат додатково перевіряється через актуальні `users.info` і `users.profile.get` перед видачею коду та після його введення. Довідник сам по собі не створює сесію або підтверджену прив’язку.

Обхід виконується частинами з обмеженням часу. Redis-lease дозволяє лише одному виконавцю зберігати прогрес і публікувати результат. Публікується атомарно повна версія; незавершений обхід не замінює чинну. Пагінація та Retry-After зберігаються між викликами. Завершення частини запускає підписаний запит продовження до фіксованого `SLACK_DIRECTORY_ORIGIN`, без редиректів. Щоденний Vercel Cron запускає оновлення; запит входу також продовжує перервану роботу. Довідник зберігається до 7 днів, але актуальність конкретного профілю перевіряється на кожному вході. Якщо LDAP не знайдено у довіднику віком понад годину, запускається оновлення. До завершення першого обходу сайт може попросити повторити запит через кілька хвилин.

Додаткова команда `/zp` без аргументів створює прив’язку лише для підписаного Slack відправника. Вона зберігається 30 днів після останнього входу; автоматичний довідник дозволяє знайти працівника й після її закінчення. Публічний endpoint входу не приймає Slack ID. Заблоковані акаунти, боти, гості та інший workspace не допускаються. Змінений LDAP не дозволяє використати стару прив’язку.

Атомарна операція Redis не дозволяє іншому Slack ID замінити підтверджену прив’язку. При переведенні логіна на інший Slack-акаунт адміністратор має відкликати стару прив’язку або дочекатися її закінчення.

## Налаштування

1. Створити Slack App із `docs/slack-app-manifest.json` і встановити у workspace. Дозволи: `users:read`, `users.profile:read`, `chat:write`, `commands`. Після додавання команди перевстановіть застосунок у workspace, щоб застосувати новий дозвіл. Читання повідомлень і email не потрібне.
2. У серверних Environment Variables Vercel задати `SLACK_BOT_TOKEN`, `SLACK_SIGNING_SECRET`, `SLACK_TEAM_ID`, `SLACK_LDAP_FIELD_ID`, `AUTH_SECRET`, `UPSTASH_REDIS_REST_URL` та `UPSTASH_REDIS_REST_TOKEN`.
3. Встановити `CORPORATE_AUTH_SOURCE=slack-profile`, `SLACK_IDENTITY_MODE=profile` і налаштувати довіру до LDAP-поля, описану нижче.
4. Увімкнути `LDAP_SLACK_ENABLED=true` і `SLACK_DIRECTORY_ENABLED=true`. Задати `SLACK_DIRECTORY_ORIGIN=https://zp-kit.vercel.app` та випадковий серверний `CRON_SECRET`. Vercel передає його в Authorization щоденного запиту о 03:00 UTC (на Hobby в межах відповідної години).
5. Після публікації запустити `/api/corporate-auth?action=directory-sync` із Bearer CRON_SECRET. Захищений тим самим секретом `action=directory-status` повертає лише кількість профілів, зіставлень, дублікатів і час. Preview не запускає Cron. Нових дозволів Slack не потрібно.
6. Дочекатися повного довідника й перевірити LDAP → OTP без попередньої `/zp`.

Під час Preview-збірки, якщо ID поля ще не заданий, скрипт показує лише ID workspace та визначення поля LDAP без профілів і секретів. Для перевірки атомарного Lua у реальному Redis можна одноразово задати `SLACK_VERIFY_REDIS_ON_BUILD=true` у Preview або запустити `node scripts/verify-redis-otp.mjs` із серверними змінними. Використовуються випадкові тимчасові ключі, які видаляються після тесту. Повідомлення не надсилаються. Після перевірки поверніть прапорець у `false`.

### Додаткова команда /zp

1. Slack App → **Basic Information → App Credentials → Signing Secret**. Значення записати у Vercel як `SLACK_SIGNING_SECRET` для потрібного середовища; у чат чи Git не вставляти. Після зміни серверних змінних потрібне нове розгортання.
2. Slack App → **Slash Commands → Create New Command**: Command **`/zp`**, Short Description **`Підключити Slack до калькулятора ЗП`**, Usage Hint залишити порожнім. Request URL — `https://<домен цього розгортання>/api/slack-command`.
3. **OAuth & Permissions → Reinstall to Workspace**. Дозвіл `commands` має бути застосований разом з іншими трьома дозволами. Якщо Slack видав новий Bot User OAuth Token, оновити `SLACK_BOT_TOKEN` у Vercel.
4. У Slack виконати `/zp` без логіна й дочекатися особистого підтвердження бота. Після цього ввести LDAP на сайті та отримати код.

У manifest використано майбутній production URL `https://zp-kit.vercel.app/api/slack-command`. До публікації цієї версії на production використовуйте URL погодженого Preview. Slack викликає Request URL зі своїх серверів, тому сторінка входу Vercel перед endpoint не підійде. Для захищеного Preview можна використати офіційний **Protection Bypass for Automation**: додати до Request URL параметр `x-vercel-protection-bypass` зі спеціальним токеном Vercel. Цей URL стає секретним і вводиться лише в налаштування Slack App; не публікуйте його в Git чи чаті. Підпис Slack усе одно обов’язковий. Для production із публічним endpoint додатковий токен Vercel не потрібен. Налаштування зовнішнього доступу й справжньої команди ще потребує інтеграційної перевірки.

Коди ролей залишаються доступними. `ROLE_CODE_LOGIN_ENABLED=false` вимикає також адміністративний код; не вимикайте їх до погодженого способу призначення адміністратора. Усі авторизовані працівники бачать 13 калькуляторів; редагування ставок доступне лише адміністратору.

## Довіра до поля LDAP

Власник підтвердив: поле заповнює IT, працівники не можуть його змінювати. За замовчуванням код вимагає `options.is_protected=true` у `team.profile.get`. Для вашого поля API повернув `false`; 10 вересня 2026 року власник повторно підтвердив фактичну заборону редагування.

Для такого випадку серверна змінна `SLACK_LDAP_FIELD_ATTESTATION` містить точну пару `SLACK_TEAM_ID:SLACK_LDAP_FIELD_ID`. Це довіра до підтверджених власником правил, а не доказ захисту з API. Налаштування діє лише для вказаного workspace і поля; відсутнє поле завжди блокує вхід. Зміна цього налаштування відкликає корпоративні сесії. Значення LDAP порівнюються цілком, без урахування регістру й крайніх пробілів.

## Коди та сесії

- Код: 6 цифр, діє 5 хвилин, одне використання, максимум 5 неправильних спроб. Повторна видача не частіше 60 секунд; 10 запитів із IP за 15 хвилин. Після підказки про відсутню прив’язку можна виконати `/zp` і одразу повторити запит коду.
- Redis зберігає HMAC коду. Lua атомарно перевіряє код, рахує спроби та видаляє використаний код. Діє лише останній виданий код для логіна.
- Після коду повторно перевіряється той самий Slack ID, активність і LDAP-поле; лише тоді подовжується прив’язка та створюється сесія. Прив’язку створює успішна перевірка OTP або додаткова підписана команда `/zp`.
- Сесія: максимум 8 годин, HttpOnly, Secure на хостингу, SameSite=Lax. Під час відкритої сесії Slack не опитується. Зміна `AUTH_SESSION_VERSION` відкликає всі сесії. Вимкнення корпоративного входу або зміна способу перевірки/workspace/поля/підтвердження довіри відкликають корпоративні сесії.
- Автотести перевіряють підпис і відправника команди, захист від повторного запиту, адресні звернення, відсутність обходу списку працівників, підтвердження OTP перед прив’язкою, відхилення конфліктів, захист поля, зміни акаунта та роботу без email і LDAP/AD. Реальний Redis перевіряється окремим інтеграційним тестом; доставку Slack потрібно перевірити на погодженому тестовому акаунті.

## Додатковий режим каталогу

Окрема перевірка LDAP/AD доступна лише при явному `CORPORATE_AUTH_SOURCE=directory`. Для неї потрібні LDAPS URL, сервісні bind DN/пароль і base DN або HTTPS-міст. Потрібно перевірити доступність каталогу з хостингу; для доступу лише через VPN міст розгортається в корпоративній мережі. Типовий фільтр налаштовано на активні Microsoft AD-акаунти; інший каталог потребує фільтра IT із `{{login}}`. У режимі `profile` email не потрібен і для цього варіанту.

Попередній варіант через email доступний лише з `CORPORATE_AUTH_SOURCE=directory` та `SLACK_IDENTITY_MODE=email`; для нього потрібні `users:read.email`, `users:read`, заповнена пошта LDAP і, за потреби, `LDAP_EMAIL_DOMAINS`. Автоматичного переходу до email при помилці профільного режиму немає.

## Контракт HTTPS-моста

Лише в додатковому режимі `CORPORATE_AUTH_SOURCE=directory`, за наявності `LDAP_BRIDGE_URL` та `LDAP_BRIDGE_TOKEN` замість прямого LDAP виконується:

```http
POST /directory/lookup
Authorization: Bearer <server-only bridge token>
Content-Type: application/json

{"login":"employee.login"}
```

Активний працівник: HTTP 200, `{"active":true,"displayName":"Ім’я"}` (email потрібен лише для окремого режиму `email`). Невідомий або заблокований: HTTP 200, `{"active":false}`. Помилка каталогу: HTTP 503. Міст має перевіряти токен, екранувати LDAP-фільтр, перевіряти активність, обмежувати частоту запитів і не логувати секрети. Міст розгортає IT у мережі з доступом до каталогу; готового корпоративного endpoint у цьому репозиторії немає.
