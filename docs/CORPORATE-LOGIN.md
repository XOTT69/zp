# Корпоративний вхід

Робочий логін → точний збіг із захищеним полем **About me → LDAP** активного Slack-профілю → особисте повідомлення з одноразовим кодом → сесія калькулятора.

За погодженням власника достатньо активного Slack-профілю, поля LDAP, яке заповнює IT, і коду зі Slack. Основний режим `CORPORATE_AUTH_SOURCE=slack-profile` не підключається до LDAP/AD-сервера, не використовує email і не просить LDAP-пароль. LDAP тут — назва робочого логіна в профілі, а не протокол автентифікації. Працівники отримують доступ до всіх 13 калькуляторів; редагування ставок залишається лише адміністратору.

## Що підготувати адміністратору

1. Створити Slack App із `docs/slack-app-manifest.json`, встановити у робочий workspace. Записати Bot User OAuth Token у серверну змінну `SLACK_BOT_TOKEN` у Vercel. Дозволи: `users:read`, `users.profile:read` і `chat:write`. Пошук працює без email; читання повідомлень не потрібне. Якщо застосунок створено за попереднім шаблоном, замінити `users:read.email` на `users.profile:read` і перевстановити застосунок у workspace. У manifest назва бота `zp-calculator` використовує дозволені латинські символи; назва застосунку залишається «Калькулятор ЗП».
2. Підключити Upstash Redis, записати REST URL і токен у змінні з `.env.example`.
3. Визначити ID workspace та захищеного поля `LDAP`, виконати синхронізацію профілів за інструкцією нижче. Установити `CORPORATE_AUTH_SOURCE=slack-profile`, `SLACK_IDENTITY_MODE=profile`, `SLACK_TEAM_ID` і `SLACK_LDAP_FIELD_ID`.
4. Налаштувати регулярне оновлення індексу; перевірити, що воно завершилося успішно.
5. Встановити `LDAP_SLACK_ENABLED=true` та redeploy. Ця змінна з історичною назвою вмикає корпоративний вхід також у режимі без LDAP-сервера. Спочатку перевірити тестового працівника в preview. Лише після успішної перевірки можна вимкнути коди ролей: `ROLE_CODE_LOGIN_ENABLED=false`. Це вимикає також адміністративний код; для адмін-панелі залишайте коди ввімкненими до окремого погодженого способу призначення адміністратора.

Секрети вводяться в Environment Variables, а не в репозиторій чи публічний чат. Шаблон не містить робочих доступів.

## Пошук за полем LDAP без email

Власник підтвердив: логін міститься в **About me → LDAP**, поле заповнює IT, працівники його змінювати не можуть. За замовчуванням код перевіряє `options.is_protected=true` через `team.profile.get`. Якщо власник підтвердив, що редагування контролює IT, але API повертає `false`, серверна змінна `SLACK_LDAP_FIELD_ATTESTATION` може містити точну пару `SLACK_TEAM_ID:SLACK_LDAP_FIELD_ID`. Це явна довіра до підтверджених власником правил редагування, а не доказ захисту з API. Вона діє лише для цього workspace і поля; відсутнє поле завжди блокує вхід. Зміна цього налаштування відкликає корпоративні сесії. 10 вересня 2026 року власник повторно підтвердив, що працівники не можуть редагувати LDAP, попри `is_protected=false` у відповіді встановленого бота. Зіставляються цілі значення без урахування регістру та крайніх пробілів. Дубльований логін не отримує коду. Боти, видалені користувачі, гості та інші workspace не включаються.

Підготовка виконується адміністратором із серверними секретами в локальному `.env.local` (файл ігнорується Git) або змінних середовища керованого сервера. Не вставляйте токени в команду чи чат.

```sh
node --env-file=.env.local scripts/sync-slack-profiles.mjs --fields
```

Команда повертає ID workspace і визначення полів, без значень профілів чи email. Виберіть поле з назвою `LDAP` і `protected: true` (або з окремим підтвердженням власника, описаним вище); запишіть його ID у `SLACK_LDAP_FIELD_ID`, а workspace ID — у `SLACK_TEAM_ID`. Вкажіть `SLACK_IDENTITY_MODE=profile`. Ці самі налаштування потрібні Vercel і процесу синхронізації.

```sh
node --env-file=.env.local scripts/sync-slack-profiles.mjs
```

Синхронізація читає всі сторінки `users.list` і поле кожного відповідного користувача через `users.profile.get`. Для великої організації це може зайняти кілька хвилин; обхід винесено з HTTP-запиту входу. Запити обмежені паузами, помилка API зупиняє синхронізацію. Redis отримує один повний індекс лише після успішного завершення; частковий результат не публікується. Зберігаються HMAC логінів і Slack ID, без email та повних профілів.

Для початкової синхронізації у Vercel Preview можна задати `SLACK_SYNC_ON_BUILD=true`: скрипт збірки використає серверні секрети та виведе лише лічильники. Помилка синхронізації зупинить цю збірку; частковий індекс не буде опублікований. Після успіху поверніть `false`, щоб не сканувати workspace при кожній зміні коду. Це не замінює регулярного оновлення.

Індекс діє 24 години. Перед увімкненням production потрібно налаштувати запуск цієї команди, наприклад кожні 12 годин на керованому сервері/CI, та після кадрових змін. Планувальник у цьому PR не підключений. Шаблон для GitHub Actions: `docs/github-workflow-slack-profiles.yml`; після отримання права `workflow` його можна встановити в `.github/workflows/` і додати перелічені в ньому secrets. Перед вибором GitHub Actions перевірте тривалість сканування та доступні хвилини CI; для великого workspace можна запускати команду на керованому сервері. Прострочений індекс блокує корпоративний вхід; коди ролей залишаються доступними. Після зміни `AUTH_SECRET`, workspace або ID поля індекс потрібно створити заново.

Перед надсиланням коду і при його перевірці повторно читаються поточний Slack-акаунт і значення захищеного поля. Зміна зіставлення або блокування користувача не дозволяють завершити вхід. Під час уже відкритої восьмигодинної сесії повторної перевірки немає. Перед production потрібно підтвердити доступність поля через API саме встановленому боту; видимість у застосунку Slack не гарантує цей доступ.

Окрема перевірка LDAP/AD доступна лише при явному `CORPORATE_AUTH_SOURCE=directory`. Для неї потрібні LDAPS URL, сервісні bind DN/пароль і base DN або HTTPS-міст. Потрібно перевірити доступність каталогу з хостингу; для доступу лише через VPN міст розгортається в корпоративній мережі. Типовий фільтр налаштовано на активні Microsoft AD-акаунти; інший каталог потребує фільтра IT із `{{login}}`. У режимі `profile` email не потрібен і для цього варіанту.

Попередній варіант через email доступний лише з `CORPORATE_AUTH_SOURCE=directory` та `SLACK_IDENTITY_MODE=email`; для нього потрібні `users:read.email`, `users:read`, заповнена пошта LDAP і, за потреби, `LDAP_EMAIL_DOMAINS`. Автоматичного переходу до email при помилці профільного режиму немає.

## Контракт HTTPS-моста

Лише в додатковому режимі `CORPORATE_AUTH_SOURCE=directory`, за наявності `LDAP_BRIDGE_URL` та `LDAP_BRIDGE_TOKEN` замість прямого LDAP виконується:

```http
POST /directory/lookup
Authorization: Bearer <server-only bridge token>
Content-Type: application/json

{"login":"employee.login"}
```

Активний працівник: HTTP 200, `{"active":true,"displayName":"Ім’я"}` (email потрібен лише для окремого режиму `email`). Невідомий або заблокований: HTTP 200, `{"active":false}`. Помилка каталогу: HTTP 503. Міст має перевіряти токен, екранувати LDAP-фільтр, перевіряти активність, обмежувати частоту запитів і не логувати секрети. Міст розгортає IT у мережі з доступом до каталогу; готового корпоративного endpoint у цьому репозиторії немає.

## Обмеження й перевірки

- Код: 6 цифр, 5 хвилин, одна успішна спроба, максимум 5 неправильних спроб. Повторна видача не частіше 60 секунд; 10 запитів із IP за 15 хвилин. Redis зберігає HMAC коду, а не сам код. Порівняння, лічильник спроб та споживання — атомарний Lua-скрипт.
- Перевіряється також останній виданий код для логіна, активність Slack-профілю й незмінність його LDAP-поля при завершенні входу. LDAP-сервер перевіряється лише в режимі `directory`. Під час уже відкритої сесії зовнішні системи не опитуються; корпоративна сесія має абсолютний термін 8 годин.
- Cookie: HttpOnly, Secure на хостингу, SameSite=Lax. Зміна `AUTH_SESSION_VERSION` відкликає всі сесії; зміна коду ролі відкликає сесії цієї ролі. Вимкнення корпоративного входу або зміна способу перевірки, Slack workspace чи ID поля відкликають корпоративні сесії.
- Автотести ізольовано перевіряють логіку й транспортні контракти. Вони не замінюють інтеграційну перевірку справжнього Slack і виконання Lua в Redis (та LDAP для додаткового режиму `directory`).
- Перед production перевірити: активний/неактивний працівник; правильний/неправильний/прострочений/повторний код; п’ять помилок; перевидача; паралельне використання одного коду; недоступність Redis та Slack. Для реальних повідомлень використати погоджений тестовий акаунт.

Офіційна документація: [team.profile.get](https://docs.slack.dev/reference/methods/team.profile.get/), [users.profile.get](https://docs.slack.dev/reference/methods/users.profile.get/), [users.list](https://docs.slack.dev/reference/methods/users.list/) і [chat.postMessage](https://docs.slack.dev/reference/methods/chat.postMessage/).
